# Audit note — T301b / T302 mobile live-verification pass (2026-08-03)

- **By:** Claude Code (Sonnet 5)
- **Scope:** the two "not blocking" follow-ups named in the 2026-08-02 re-audit
  ([T30x batch audit](T30x-batch-signoff-audit.md)): secure token persistence, and an on-device
  offline→online sync cycle against a live backend. T301b/T302 were already `DONE` — this pass
  does not re-flip their status, it closes/advances the named follow-ups.

## Results

- **`flutter analyze`: no issues found.**
- **`flutter test`: 40/40 pass** (12 pre-existing + 28 added this pass).
- Added real test coverage for the four areas the 2026-08-02 audit flagged as untested: the sync
  engine, sync queue, api client, and auth flow (`test/sync_engine_test.dart`,
  `test/sync_queue_test.dart`, `test/api_client_test.dart`, `test/auth_state_test.dart`).
- **Secure token persistence: implemented.** `flutter_secure_storage` + a new
  `TokenStore`/`SecureTokenStore` abstraction (`lib/core/storage/token_store.dart`);
  `AuthNotifier` persists on login, clears on logout, and exposes `restoreSession()`; `main()`
  now restores the session before `runApp` so a restart doesn't strand an authenticated
  contractor or their queued sync mutations behind the login screen.
- **Real bug found and fixed** by the new `sync_engine_test.dart` coverage (not a pre-existing
  known issue): `pullCustomers`'s conflict-resolution path merges the server payload and the
  local SQLite row by exact key name. The wire format uses `display_name`; the local column is
  `name`. A newer local rename could therefore never win — `display_name` rode through untouched
  and `LocalDatabase.upsertCustomer`'s `display_name ?? name` fallback silently kept the stale
  server value. Fixed by aliasing `display_name` → `name` before resolution
  (`lib/core/sync/sync_engine.dart`). Quotes didn't have this bug — their field names already
  matched 1:1.
- **On-device offline→online sync cycle: not completed here.** No Android emulator is available
  (`flutter emulators` found none) and the Docker daemon is unreachable in this environment
  (`docker ps` fails to connect; Docker Desktop was launched and polled for ~4 minutes without
  the daemon coming up — consistent with the same constraint noted in prior T202b/T204b/T307b
  handoffs). Per the user's direction mid-session, this step was reassigned rather than worked
  around locally: see
  [T301b-T302-mobile-live-verification-antigravity-handoff.md](T301b-T302-mobile-live-verification-antigravity-handoff.md).

## What's NOT claimed

This note does not claim the offline→online sync cycle was verified live, does not claim the
conflict resolver was exercised against a real gateway, and does not claim the secure-storage
write/read path was exercised on real iOS Keychain/Android Keystore hardware (only via the
injectable `TokenStore` fake in unit tests). Those remain the Antigravity handoff's job.
